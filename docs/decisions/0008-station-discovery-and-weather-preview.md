# ADR 0008: Station discovery and a bounded, separate weather preview

Date: 2026-10-02

## Context

The owner requested Phase 3 of the current roadmap while observing the newly deployed Phase 2 operations work. Developing this user-facing milestone does not close Phase 2's measured observation or real degradation-notification evidence. Visitors need to find a gauge, interpret its data age and provenance, and share its page on mobile without a map, color, or hover.

## Decision

- Search the six configured gauges by name or WSC ID, filter by broad gauge-location groups (Cape Breton, eastern mainland, South Shore), and sort by experimental score, measured observation freshness, score-input completeness, or name. Groups describe locations, not watershed boundaries, access, or legal eligibility. Metadata names come from the existing station seed file. Unknown future IDs use an explicit other-stations group until reviewed.
- For score/completeness sorting, complete scores precede partial scores, then null scores. Sort available rule-point coverage within completeness tiers; this is score-input completeness, not a claim about sensor or river coverage. Freshness sorts current readings, stale readings, unassessed readings from older APIs, and missing readings separately. Add API-evaluated `flow_state` and `flow_age_minutes`; do not equate complete score inputs with fresh measurements. Keep the current three-hour discharge threshold, including its exact inclusive boundary. Operator diagnoses remain on `/status`.
- Use numbered, keyboard-focusable map markers, a written status legend, and matching station links with status text. Fit the map to the filtered stations. Stale measured flow, missing flow, complete/partial score, and unavailable score are distinct. No core information requires map tiles to load.
- Show discharge on a proportional time axis with straight lines between available readings. Preserve the existing visible-gap convention (>90 minutes); this display convention differs from Phase 2's station-cadence diagnostics and is not an estimate of missing measurements. Include every returned timestamp, unit, qualifier, and approval in a scrollable, keyboard-accessible table. Weather history is a separate chart/table, never a second measured river series.
- Add `GET /api/v1/stations/{id}/weather?history_hours=48&forecast_hours=24`. Bound history to 1–168 hours and preview to 1–24 hours. Return only stored rows, null values, their classification, and retrieval time; never call a provider during a web request. Historical/model rows must end at or before the current UTC hour. Forecast rows must have a valid time after the evaluation time. Expired forecast rows never become history. Invalid queries return 422; unknown stations return 404; known stations with no weather return 200 with empty arrays and explicit window bounds.
- Preserve the existing `weather_hours` latest-version key and one-forecast-day ingestion request. No migration, retention change, or new provider fetch is required for this preview. Some of the next 24 hours may be missing, especially near the end of the provider's requested day. The UI enumerates each expected hour and shows coverage instead of claiming a full-day forecast. Missing fields remain unavailable, and reported zero precipitation stays distinguishable from missing precipitation.
- Expose `ingested_at_utc` as `retrieved_at_utc`, not provider issue/model-run time. `provider_issued_at_utc` is explicitly null because it is not retained. Per-row retrievals older than three hours are labeled stale. This is a conservative display convention, not calibrated forecast confidence. Keep valid future hours visible with their stale retrieval warning. Do not imply that older historical-weather retrievals are invalid history.
- Show a separate forecast section with air temperature, precipitation, cloud cover, valid/retrieval timestamps, source, missing hours, and the explicit no-future-score boundary. No forecast enters scoring, and this is not a seven-day planner or river-flow forecast. A weather endpoint failure leaves the measured-data and score sections usable. Station-specific metadata carries stable descriptive information, not a score/reading that can expire after sharing. A copy-link action has a selectable-link fallback when clipboard access fails.

## Provider interval discovery and existing discrepancy

[Open-Meteo's hourly definitions](https://open-meteo.com/en/docs), checked on 2026-10-02, specify precipitation as the **sum of the preceding hour**, including rain, showers, and snow water equivalent. Air temperature and cloud cover are instantaneous at the labeled hour. Accordingly, a 48-hour precipitation history ending at UTC hour H selects interval-end timestamps `(H − 48h, H]`; the UI explicitly explains this.

The current specification and score implementations select precipitation timestamps `[H − 12h, H)` (and analogous shadow windows). With provider interval-end semantics, that represents a window ending one hour earlier than the displayed 12-hour label suggests. This change **does not silently shift any deployed score window or rules version**. A separate versioned scoring decision, replay, tests, and rollout are required to reconcile it. The new weather history must not be presented as a direct reproduction of a score's precipitation sum.

## Verification and release limits

Local API and browser verification is recorded in the Phase 3 section of the roadmap after running the checks. No production deployment, real-phone verification, seven-day forecast coverage, forecast-error calibration, or improvement in fishing accuracy is claimed. A physical narrow-screen phone check remains a release gate. Phase 4 must decide forecast issue/version retention, seven-day ingestion, Atlantic daily boundaries, and provider licensing before building the Trip Planner.
