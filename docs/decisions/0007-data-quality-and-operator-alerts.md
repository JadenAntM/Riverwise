# ADR 0007: Diagnose data gaps and alert operators without changing the score

Date: 2026-10-02

## Context

The existing status page reported provider attempts, observation age, and aggregate revision counts. It could not tell an operator whether stale discharge reflected a failed request, invalid provider content, an otherwise successful import with no new measurement, or a scheduler delay. A revision count also did not retain the changed source fields. This is operational diagnosis, not an accuracy claim or a new fishing-condition rule.

## Decision

- Keep the three-hour discharge age threshold used by the current score. In status reporting, classify an old reading as a provider error, invalid payload, missing measurement, delayed publication, or stale import according to the latest WSC run. A successful WSC import within 90 minutes with old discharge is *delayed publication*, not proof the sensor or provider is broken. Fresh discharge remains current even if an isolated subsequent import fails; the failed source run is shown separately.
- Derive descriptive gap counts from each station's stored discharge timestamps in the requested seven- or 30-day window. The threshold is the larger of one hour and three times that window's median observed interval. This is an observed cadence estimate, **not** a promise of WSC publication frequency or a percentage-completeness claim. Fewer than two readings yield no cadence estimate.
- Validate plausible source ranges before writing: Open-Meteo air temperature −80 to 60°C, precipitation 0 to 500 mm/hour, cloud cover 0 to 100%, and surface pressure 800 to 1100 hPa. Null weather fields remain missing; an all-null response is a missing-measurement failure. Exact duplicate hydrometric rows are collapsed; conflicting duplicates fail the source import. These broad bounds catch corrupt data, not anomalous-but-real conditions. A changed stored WSC value, unit, qualifier, or approval creates a prospective old/new audit row. Past revisions cannot be reconstructed.
- Store an error category with each new failed provider run and put its database run ID in structured source logs and the public status response. Categories are provider timeout, HTTP error, network error, missing measurement, invalid payload, or internal error. Existing runs have a null category.
- Open a deduplicated operator alert after three consecutive failures for a station/source, when an import has not run for 90 minutes, or when no discharge reading is within three hours. Resolve it when the condition clears. An optional webhook receives a JSON POST on opening, at most once every six hours while the alert remains active, and on resolution if it had previously been delivered. Store delivery state; a failed webhook call does not erase the alert. The webhook URL is an environment secret and is never included in logs or the public API. Until a destination is configured, detection and status display work but **no off-app notification is delivered**.
- Expose current findings on `/api/v1/ingestion` and an operational-health endpoint that returns HTTP 503 for degraded data. This endpoint is distinct from `/health`: process/database health can be normal while ingestion needs attention. An external monitor is needed to detect total scheduler or API downtime in real time; a stopped scheduler cannot send its own alert.

Resolution webhooks are best-effort and are not retried after a delivery error in this iteration; the public status and stored resolution state remain authoritative. Configure a destination that treats the alert key as an idempotency key and reconcile against the status endpoint when needed.

## Consequences and verification

This adds three forward-only migrations: run error category, hydrometric revision audit, and alert state. The current `v1.0.0` dashboard score and both shadow rules are unchanged. The status UI explains states in text and does not require color. The repository includes parser, diagnosis, deduplication, webhook-delivery, PostgreSQL integration, and browser tests. Production rollout evidence is below; confirmed email receipt and a measured post-deployment observation window remain open.

On the local PostgreSQL 17 development database on 2026-10-02 (63,138 hydrometric rows and 495 stored ingestion runs), read-only `EXPLAIN (ANALYZE, BUFFERS)` showed the seven-day timestamp lookup for station `01FB001` returning 1,990 discharge times via the existing `ix_hydro_station_parameter_time` index in 0.498 ms execution time. The latest-three-`wsc`-runs query used the existing `ix_ingest_source_station_time` index and took 0.136 ms. These are two local SQL-query measurements, not end-to-end API latency or production service-level results; no additional index was added for these read paths. The revision-audit index is on a new table and supports station/time review of changed fields.

At 2026-10-02 22:21 UTC, the owner requested email monitoring and a free UptimeRobot monitor setup request was submitted for the existing public API `/health` endpoint. The owner activated it, and the dashboard showed that monitor Up with a five-minute interval and their email contact. This first monitor checks API/database reachability only.

On 2026-10-02, a fresh production PostgreSQL custom-format export was written at 22:48:20 UTC and validated with `pg_restore --list` and SHA-256. It restored into a separate local PostgreSQL database: six stations, 61,885 hydrometric rows, 6,366 score snapshots, and 5,556 ingestion runs. Migrations 0004–0006 applied successfully there; API smoke checks returned 200 for `/health`, `/api/v1/operational-health`, and `/api/v1/ingestion`. All three GitHub CI jobs passed. The same migrations were applied to production before merging [PR #3](https://github.com/JadenAntM/Riverwise/pull/3) as commit `3edaade`.

After the merge, Railway reported the API and web services Online and the new scheduled-ingestion image deployed. At 23:04–23:05 UTC, its first run completed successfully; all six WSC and six Open-Meteo current station imports succeeded with run IDs 5557–5568, all station discharge states were current, and `GET /api/v1/operational-health` returned 200 with zero alerts. The public `/status` page returned 200.

A second free UptimeRobot monitor was created for `/api/v1/operational-health` at a five-minute interval with the owner's email contact. Its first check returned a **false 405 incident**: the free HTTP monitor sends HEAD by default, while the endpoint initially accepted only GET; selecting GET prompted for a paid plan. The monitor was paused while a tested HEAD route mirroring GET's 200/503 status was prepared ([issue #4](https://github.com/JadenAntM/Riverwise/issues/4)). The first incident is a monitor compatibility problem, not evidence of failed ingestion. Do not count it as genuine ingestion downtime. Confirm the resumed monitor and actual email receipt before claiming external alert delivery is operational.
